## Phase 1 — Brainstorm

Path: `docs/brainstorms/2026-06-02-openvpn-interactive-auth-requirements.md`

Two architectural approaches were considered:

- **Approach A: SCRV1 envelope on line 2 of the auth-user-pass file.** OpenVPN's documented format. Client writes `<username>\nSCRV1:base64(password):base64(otp)\n` to the auth file; openvpn reads it as part of `--auth-user-pass <file>` setup; no daemon-mode changes. The fast / minimum-change path.
- **Approach B: Foreground supervised openvpn + management socket.** Client drives the entire auth dance over `--management <unix-socket>` while openvpn is suspended via `--management-hold`. Mirrors what Mullvad, NordVPN, Tunnelblick, NetworkManager all do.

After dialogue, the user picked Approach A based on "fix this issue only, no rewrite." The brainstorm wrote in a **Pre-merge Gate** requiring the implementer to verify with a `--verb 4` log against the reporter's actual server that SCRV1-in-auth-file works on OpenVPN 2.7 before merging.

## Phase 5 — Pivot to Approach B-minimal (management socket)

User authorized "ship it." Plan: read Mullvad's `talpid-openvpn` (their open-source OpenVPN wrapper) for the management-socket pattern, then re-implement in vortix under MIT (cleanroom; protocol is public).

Commit: `2a597ff` — `feat(openvpn): management-socket flow for static-challenge (#191, Approach B-minimal)`. Key changes:

- `write_openvpn_scrv1_auth_file` now writes a **3-line credentials bundle** (`user\npass\notp\n`), NOT an SCRV1 envelope. This is a transient handoff file from the submit handler to the protocol layer — openvpn never reads it. Path: `<auth_dir>/<safe_name>.scrv1.auth`. Mode 600.
- `OvpnTunnel::up()` checks for the bundle file. When present:
  - Reads + deletes the bundle.
  - Builds openvpn argv with `--management <sock> unix --management-hold --management-query-passwords --daemon` (NO `--auth-user-pass` — creds come via socket).
  - Spawns openvpn on a worker thread (`run_to_output` blocks until the parent forks/exits, which only happens after auth completes).
  - On the main thread: polls for the unix socket to appear, connects, drives `drive_mgmt_auth`.
- `drive_mgmt_auth` implements the static-challenge-inline path:
  - On `>HOLD:` → `hold release`
  - On `>PASSWORD:Need 'Auth' SC:1,<prompt>` → `username "Auth" "<u>"` + `password "Auth" "SCRV1:base64(p):base64(o)"`
  - On `>PASSWORD:Need 'Auth'` (non-SC variant) → plain user/pass over socket
  - On `>STATE:<ts>,CONNECTED,...` → return Ok
  - On `>PASSWORD:Verification Failed` → return AuthFailed
  - On `>FATAL:` → return DaemonExited
  - Other prompt kinds (Private Key passphrase, etc.) → return AuthFailed with "not yet supported" message (loud-fail, deferred to next brainstorm)
- Non-MFA OpenVPN profiles (no `static-challenge` directive, no bundle file) keep the legacy `--auth-user-pass <file>` + log-poll flow byte-for-byte.

`AUTH_FAILED` with no `CRV1:R,E,...` payload after it means the server is NOT doing dynamic CRV1 — it's running static-challenge PAM and returning a flat reject. So either pam_unix (system password check on user `vortix`) or pam_google_authenticator (OTP check) is failing.

## Phase 7 — Wrong diagnosis, reverted

I committed `dd41603` — *"fix(test-infra): remove username-as-common-name from ovpn-auth + ovpn-totp"* — speculating that `username-as-common-name` in the server config was causing PAM to be called with the cert CN (`client-totp`) instead of the auth-user-pass username (`vortix`).

User correctly challenged: "ovpn-auth works for me with `vortix`/`testpass123` and it has the same directive — so your diagnosis can't be right." Verified against OpenVPN docs: `username-as-common-name` overrides the CN used for downstream lookups (iroute, client-config-dir) but **does not** change the username passed to the auth plugin. The PAM plugin always receives the auth-user-pass username regardless.

Reverted in `8a11a29` — *"Revert "fix(test-infra): remove username-as-common-name from ovpn-auth + ovpn-totp""*. The script is back to its original state.

## Likely outcomes and the matching fixes

| Server log says | Real cause | Fix in `scripts/test-infra.sh` cloud-init |
|---|---|---|
| `pam_unix(openvpn-totp:auth): authentication failure ... user=vortix` AND `passwd: locked` in /etc/shadow | `useradd -m -s /bin/false vortix` left the account locked; `chpasswd` may not unlock on Ubuntu 24.04 | Add `usermod -U vortix` after `chpasswd`, OR use `chpasswd -e` with a pre-hashed password, OR change the shell to `/usr/sbin/nologin` which some PAM configs treat differently |
