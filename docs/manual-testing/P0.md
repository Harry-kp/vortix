# P0 — release gate

The checks that only a real kernel, a real terminal and real protocol daemons can answer,
run on **macOS and Linux** before a release ships. Anything an automated test can decide is
not here (see [What this file does not cover](#what-this-file-does-not-cover)).

Every step is a literal command or keystroke, and every pass signal is something you can see
in captured output. A step that needs judgement is a bug in the step.

## Strategy: four passes, in order

Walking all 47 workflows on both machines takes most of a day, so every release walks the
same short core and spends the rest of the time where the release changed code.

| Pass | What | When it stops the release |
|---|---|---|
| 1. Gate | `scripts/ci-local.sh` on the Mac, `cargo test -p vortix` on the Linux lab (runs the Linux-only code) | any red |
| 2. Smoke | `sudo scripts/p0.sh` on both machines, about 6 minutes each ([the smoke set](#pass-2-smoke-set)) | any FAIL |
| 3. Risk | `git diff --stat <last-tag>..HEAD -- crates/`, map each touched path to its workflows with the [area table](#pass-3-risk-map), run those on both machines | any fail in a touched area |
| 4. Explore | 15 minutes per machine trying to break what changed: interleave the TUI and CLI, race keys, pull the network | a finding that a user would hit |

Run the **whole** file only when the engine (`control/`), a firewall or DNS backend, or the
protocol layers changed broadly, or for a major version. Log every run in the
[results log](#results-log), including the passes you skipped and why.

**Every finding gets a regression test before its fix**, where one can exist (`control/`,
`app/tests.rs`, render tests), so the next release does not depend on a human noticing it again.

## Safety rules

These are not style: each one records a run that cut someone off.

- **Egress-blocking states are released in the same command that probes them.** On the Mac
  (the user's own machine) chain the probe and `vortix killswitch off` / `release-killswitch`
  in one root-shell command, and keep the blocked window to seconds. Longer blocking checks
  run on the lab, where `vpn-only` keeps the LAN (and so SSH) allowed.
- **Probe egress with a target that works without the VPN.** `1.1.1.1` is not reachable from
  every LAN, and a probe that fails with no VPN "proves" a kill switch that is not there. Record
  a baseline first: `curl -s -m 3 -o /dev/null -w '%{http_code}' -H Host:example.com
  http://<example.com IPv4>` must print `200` with the kill switch off.
- **On the lab, never connect a profile that routes `192.168.0.0/16`.** It carries SSH.
- **Credentials are typed by the user.** Lab profiles with saved credentials are fine; never
  print, copy or commit a profile, key or password. Redact public IPs in shared notes.
- **Leave the host as you found it:** kill-switch mode, theme, every tunnel disconnected,
  `pfctl -a com.apple/vortix.killswitch -sr` / `nft list table inet vortix_killswitch` empty.
- **Quit the TUI (`q`) before CLI lifecycle checks.** It holds the lifecycle lock, and a
  second process refuses by design (P0-04).

## Harness

The dashboard is a full-screen TUI, so drive it through `tmux` and read frames with
`capture-pane`.

Machines, sessions and access rules are in `CLAUDE.md` ("Live testing (macOS)" and
"(Linux)"). On the Mac, never type `sudo` (the `vxrun` panes are already root) and never kill
`vxrun`. Its root shell is `zsh` with the user's aliases (`wg`, `ls`, …), so call tools by full
path (`/opt/homebrew/bin/wg`, `/bin/ls`) or run a `bash` script.

```bash
VX=$PWD/target/debug/vortix         # build first: cargo build -p vortix

tui()  { tmux resize-window -t vxrun:0 -x "${1:-120}" -y "${2:-40}"
         tmux send-keys -t vxrun:0 "clear; $VX" Enter; sleep 6; }
key()  { tmux send-keys -t vxrun:0 "$@"; sleep "${DELAY:-2}"; }
frame(){ tmux capture-pane -t vxrun:0 -p; }
stop() { tmux send-keys -t vxrun:0 q; sleep 2; }              # quits the TUI, keeps the pane
```

- `tui 80 24` runs the 80×24 layout the dense workflows require.
- Assert with `frame | grep -n …`. Capture **before and after** every keystroke that is
  supposed to change something; a pass that cannot be seen in a frame is not a pass.
- The TUI needs root and refuses without it, so no TUI workflow has an unprivileged subset.
- Measure widths in characters, not bytes (a box-drawing glyph is 3 UTF-8 bytes). The Event
  Log prints `INFO` by design; look for `panicked|RUST_BACKTRACE|thread 'main'` instead.

**Keymap** (from the `?` overlay — do not guess these):

| Key | Action | Key | Action |
|---|---|---|---|
| `c` / `Enter` | connect / disconnect focused row | `i` | import profile |
| `c` (in-flight) | cancel connect | `R` | rename profile |

| `d` | disconnect focused row (sidebar) | `v` | view config |
| `D` | sidebar: disconnect **all** (`y`/`n` only with 2+ up); elsewhere: disconnect | `a` | manage OpenVPN auth |
| `r` | sidebar: connect; elsewhere: reconnect | `A` | clear saved auth |
| `K` | cycle kill switch | `s` | cycle sort |
| `p` | switch theme | `/` | search |
| `x` / `b` | action / bulk menu | `y` | copy IP |
| `j`/`k` | move selection | `F1`–`F5` | focus Sidebar … Logs |
| `z` | zoom panel | `f` | flip (Chart, Details, Security) |
| Logs: `f` / `L` | cycle source and filter / clear | `?` | help |

## A. Startup and privilege

### P0-01 — Vortix refuses cleanly when it cannot own a terminal or root
```bash
$VX                                  # no sudo
sudo $VX </dev/null >/tmp/o 2>/tmp/e ; echo "exit=$?"
sudo $VX | cat
```
**Pass** — unprivileged prints `Vortix needs administrator access to manage VPN connections.`
and `Try again with: sudo vortix`. Every non-TTY invocation exits 1 with `The Vortix dashboard
needs an interactive terminal` and names the headless commands.
**Fail** — a panic, exit 101, or a `ratatui`/`~/.cargo/registry` path in the output.

### P0-02 — A first run leaves nothing group-readable
Set a permissive umask rather than needing a 002-default distro.
```bash
mv ~/.config/vortix ~/.config/vortix.bak      # restore it afterwards
( umask 002; $VX import <profile> )           # unprivileged, before any sudo run
sudo $VX up wg07 && sudo $VX down wg07
ls -land ~/.config/vortix ~/.config/vortix/{profiles,sessions,logs}
```
**Pass** — every directory is `drwx------` and every file `0600`, owned by you. Then
`chmod 755 ~/.config/vortix ~/.config/vortix/profiles; $VX list` repairs the modes.
**Fail** — any group or world bit, or `persisted control state is not a private owner-controlled file`.

### P0-03 — An unprivileged CLI still works after a sudo session
From a fresh config directory: `sudo $VX` (let the TUI draw, then `q`), then
`$VX list; $VX status; $VX import <path>; ls -lan ~/.config/vortix/profiles ~/.config/vortix/lifecycle.lock`.
**Pass** — all three commands work; every file is owned by your uid.
**Fail** — any uid 0 in the listing, or `could not open its session lock`.

### P0-04 — A second instance refuses in one sentence
`tui 80 24`, then `$VX` from another pane.
**Pass** — the second process exits at once with one plain sentence saying Vortix is already
running; the first session is unaffected.
**Fail** — an errno, a backtrace, a source location, or the first session disturbed.

### P0-05 — A missing VPN tool warns once and blocks nothing else
Linux: `sudo apt remove -y wireguard-tools`, then `tui` (reinstall afterwards).
**Pass** — exactly one `'wireguard-tools' not found` warning naming the distro's install
command; OpenVPN profiles, listing and import still work; `up` on a WireGuard profile exits 5
with the install hint.
**Fail** — a repeating warning, or a missing tool blocking unrelated work.

### P0-06 — `vortix report` never blocks without a terminal
`$VX report </dev/null; echo "exit=$?"` and `$VX report | cat`.
**Pass** — each prints the report and exits 0 promptly.
**Fail** — a hang, or a loop on `Invalid choice`.

## B. Profile lifecycle

### P0-07 — Import accepts every supported shape and reports partial batches honestly
```bash
$VX import <lab-profiles-dir>        # mixed .conf/.ovpn, >8 files, one malformed
$VX import <single.ovpn> --json
```
Repeat the directory import from the TUI (`i`) while holding `j`/`k`.
**Pass** — every valid profile admitted once in filename order, the invalid one reported once,
the exit code reflects partial success, the terminal stays responsive, and `--json` carries no
config or credential material.
**Fail** — a valid profile silently dropped, a frozen terminal.

### P0-08 — Malformed input is refused with a reason the user can act on
Import an empty file, `[Interface]` with no `[Peer]`, a blank file, a 5 MB file, and a
filename that cannot be an interface name.
**Pass** — each refusal names its rule: `File is empty`, `Missing [Peer] section`, `Missing
[Interface] section`, `File too large … should be under 1 MB`, the naming rule.
**Fail** — a refusal with no reason, or a generic `import failed`.

### P0-10 — Rename preserves identity; delete waits for a real disconnect
Connect `03-openvpn-tcp-password-full` with saved credentials. In the TUI focus it: `R` and
`Del` are refused while active. Disconnect, rename, restart Vortix, connect again.
**Pass** — refusals give a reason; after rename the id is unchanged, saved credentials still
work, and no old-name files remain. `Del` opens on Cancel and succeeds once Disconnected.
**Fail** — a credential re-prompt after rename, an orphan file, a delete accepted mid-`Disconnecting`.

### P0-11 — A stray metadata file explains itself instead of bricking the CLI
`touch ~/.config/vortix/profiles/.stray.meta.toml; $VX list`
**Pass** — the error names that path, explains the inventory, and ends with a `mv` command that
makes `vortix list` work when run verbatim. `down`, `status` and `release-killswitch` still run.
**Fail** — a refusal with no path and no command.

## C. Connect and disconnect

### P0-12 — A cold one-shot CLI connects and disconnects on the first try
No TUI running.
```bash
sudo $VX up wg07 --timeout 60; echo "exit=$?"
$VX status; sudo $VX status --json | jq '.data.primary'
sudo $VX down wg07; echo "exit=$?"
```
Repeat for `01-openvpn-udp-full-inline`, and in `--json` and `--quiet`.
**Pass** — the first invocation converges. Human mode names the transition, target, deadline
and Ctrl-C behaviour before it waits and ends on a success line; `--json`/`--quiet` gain no
progress text.
**Fail** — a first-run timeout that a retry fixes, or progress prose in structured output.

### P0-12a — Lifecycle verbs are idempotent and say so
Measure exit codes directly (`cmd >/dev/null 2>&1; echo $?`), not through a pipe.

| Command | Expected output | Exit |
|---|---|---|
| `up <profile>` twice | second prints `● Connected to <profile> (<proto>)` | 0 |
| `down <profile>` twice | second prints `Already disconnected` | 0 |
| `down` with no argument | `Disconnecting active VPNs …` then each profile | 0 |
| `down` / `reconnect` without root | `VPN operations require root privileges` | 2 |
| `up no-such-profile` | `Profile 'no-such-profile' not found` + `Run 'vortix list'` | 3 |
| `up <conflicting>` without `--yes` | names **both** profiles and the `--yes` bypass | 4 |
| `up <profile>` with its tool missing | the install hint | 5 |
| `import <malformed>` | names the rule broken | 1 |

**Pass** — every row matches, and `down` with no argument leaves zero tunnel interfaces.
**Fail** — codes that do not distinguish 3 from 4 from 1, or an idempotent repeat that errors.

### P0-12b — Two clients racing the same profile produce one tunnel
Start `sudo $VX up wg08 --timeout 60` twice, one second apart, and wait for both.
**Pass** — both print `● Connected to wg08`, both exit 0, exactly one interface exists.
**Fail** — two interfaces, or a duplicate protocol child.

### P0-12c — `reconnect` ends connected, or says the tunnel is down
```bash
sudo $VX up wg08 --timeout 60
sudo $VX reconnect wg08; echo "exit=$?"
sudo $VX reconnect                   # no argument: every active tunnel
sudo $VX down; sudo $VX reconnect    # nothing up: the last-used profile
```
**Pass** — the profile is Connected afterwards and egress is still the VPN's. With nothing up,
`reconnect` connects the last-used profile. A genuine failure says the tunnel is **down**.
**Fail** — "nothing was changed" while the tunnel is gone and egress is the ISP's.

### P0-12d — Every protocol variant connects and tears down clean
One at a time: `wg09` (hostname endpoint), `wg10` (IPv6 endpoint), `wg11` (dual-stack),
`wg12` (preshared key), `wg13` (two peers), `wg15` (`FwMark`), `01` (inline cert), `02`
(OpenVPN split), `05` (dead first remote, must fail over).
**Pass** — each reports `● Connected`, `wg13` installs both peer routes, `05` reaches the working
remote, `wg11` on macOS binds `::/1` and `8000::/1`, and the interface count ends at zero.
**Fail** — a variant failing to connect, or a leftover interface.

### P0-12e — Rapid and interrupted lifecycle actions leave no debris
Each case starts disconnected and ends with the interface count at zero
(`ip -brief link show | grep -cE 'wg|tun'`; macOS `ifconfig | grep -c '^utun[4-9]'`).

| # | Action | Expected |
|---|---|---|
| a | `up wg08 &`, then `down wg08` ~2 s later | both report their own outcome; ends disconnected |
| b | `up`/`down` the same profile 5× back to back | ends disconnected, no stuck `Connecting` |
| c | SIGINT the client mid-connect | the connect may finish; root `status` must then report it |
| d | TUI: `Enter` then `c` while the row shows `◐` | row returns to disconnected |
| e | TUI: `7`,`8`,`9` 0.2 s apart | every one is acted on (connected or a conflict prompt) |
| f | TUI: with 2+ up, `D` then `y` | count 0 and **stays** 0 |
| g | TUI: `D` with nothing connected | no dialog |

**Fail** — a stuck `Connecting`, a leftover interface or `openvpn` process, or `status` saying
`Disconnected` while an interface carries traffic.

### P0-13 — The TUI drives the same lifecycle as the CLI
`tui 80 24`, connect by digit, disconnect with `d`; repeat with `c`/`Enter` and `r`.
**Pass** — header, sidebar badge and Security Guard move together; disconnecting from the CLI
in another pane is reflected within a tick.
**Fail** — the TUI needing a restart to catch up.

### P0-14 — Rejected OpenVPN credentials reopen the prompt next time
`03-openvpn-tcp-password-full`: connect with a **wrong** password and *save* on; connect again;
connect with the right password; disconnect; connect a fourth time; press `a`.
In the form, `Ctrl+U` must clear a field and no `Ctrl`/`Alt` chord may type a letter.
**Pass** — attempt 1 fails with an authentication error and removes the saved pair; attempt 2
reopens the prompt; attempt 3 succeeds; attempt 4 connects with no prompt.
**Fail** — a silent failure without a prompt, a remembered wrong password, or a stray letter in a field.

### P0-15 — The OpenVPN static challenge is one-shot and memory-only
`04-openvpn-tcp-static-challenge` with username and password saved: connect and answer the OTP.
**Pass** — one challenge per attempt; no `*.scrv1.auth` ever written; the OTP appears nowhere
under `~/.config/vortix` or in `ps`; the next connect prompts again.
**Fail** — the OTP on disk or in a process argument list.

### P0-16 — An unreachable peer times out, cleans up, and says so
Build the fixture from a **split-route** profile only (a full tunnel installs the default
route and resolver before the handshake and can strand the host):
`sed 's/^Endpoint =.*/Endpoint = 192.0.2.99:51820/' wg07.conf > /tmp/wgdead.conf`, import it, `up wgdead`.
**Pass** — it never claims Connected, ends at the timeout with a message naming the missing
handshake, removes the interface without reconnecting, and a retry is accepted. The default
route and `curl` still work after each attempt.
**Fail** — a reconnect loop, a leftover interface, or a UI stuck in Connecting.

### P0-17 — Disconnect reaches terminal truth without a restart
Up `wg07` and `01-openvpn-udp-full-inline`, `down wg07`. Repeat after killing the tunnel
underneath Vortix (`sudo pkill openvpn` / `sudo ip link delete <iface>`).
**Pass** — the selected profile leaves `Disconnecting` promptly, the other stays Connected, and
both paths report a plain disconnect.
**Fail** — a stuck `Disconnecting`, or Vortix DNS left on a dead link.

### P0-18 — Two tunnels own the routes they claim
Up `wg08` (full), then `wg07` (split).
```bash
route -n get 1.1.1.1; route -n get 10.200.0.1     # macOS
ip route get 1.1.1.1; ip route get 10.200.0.1     # Linux (full WG uses table 51820)
```
**Pass** — the default path resolves to the full tunnel and the split destination to the split

**Fail** — a split tunnel holding the default route, or a primary the kernel disagrees with.

### P0-18a — A `redirect-gateway def1` full tunnel is the exit, never "no exit"
Connect `01-openvpn-udp-full-inline` from the TUI several times (it was a timing race).
**Pass** — the header shows `CONNECTED`, Connection Details `Role: Primary`, Security Guard's

route stays on the LAN.

### P0-18b — Every multi-tunnel combination tells one story

| 1 | F1 | F1 | — | F1's address ✓ | none |

### P0-19 — A route conflict offers Switch or Cancel, never a dead end
With `wg08` up, connect another full tunnel: from the TUI, and from the CLI with and without
`--yes`. Include an OpenVPN full tunnel whose default route exists only in `PUSH_REPLY`.
Then the same-server case: with `wg08` up, `up 01-openvpn-udp-full-inline` (it coexists: its
full route is only pushed), then `up 01-openvpn-udp-full-inline --yes`, and probe egress.
**Pass** — the TUI modal names both profiles and offers `[Y] Switch` / `[N]`/`[Esc] Cancel`
(`Tab`, `h`, `l` move the selection and `Enter` confirms it). The CLI without `--yes` exits 4 naming both; with `--yes` the old tunnel
is stopped and only the new one remains. After the same-server switch the server's host route
is still pinned to the physical gateway and egress works.
**Fail** — both tunnels left up, a frozen modal, a toast with nothing to act on, or a switch that
leaves the new tunnel Connected but carrying nothing.

### P0-20 — A CLI disconnect does not clobber the other tunnel's protection
TUI open with `wg08` + `wg07` up and `vpn-only`; `sudo $VX down wg08` from another pane.
**Pass** — the firewall keeps `wg07`'s allowance and the TUI converges without a restart.
**Fail** — `wg07` losing its allowance because a sibling disconnected.

## E. Kill switch

Vocabulary is fixed: `off`, `block-on-drop`, `vpn-only`; `auto`/`always` are rejected with
`Use: off, block-on-drop, vpn-only`. Follow the [safety rules](#safety-rules): release in the
same command, probe a target that works without the VPN. The recovery is
`sudo vortix release-killswitch`.

### P0-21 — `vpn-only` blocks without a tunnel and passes through one
One script, ending in `off` whatever happens:
```bash
probe() { curl -s -m 3 -o /dev/null -w '%{http_code}' -H Host:example.com http://$IP || echo blocked; }
probe                                   # off: 200
sudo $VX killswitch vpn-only; probe     # no tunnel: blocked
sudo $VX up wg08; probe                 # through the tunnel: 200
sudo $VX down; probe                    # blocked again
sudo $VX killswitch off; probe          # 200
```
Read the rules at each step (`pfctl -a com.apple/vortix.killswitch -sr` / `nft list table inet vortix_killswitch`).
**Pass** — the probe results above; rules present in `vpn-only` whether or not a tunnel is up;
`$VX killswitch` says `VPN-only`; on Linux, SSH over the LAN survives.
**Fail** — any egress with no tunnel, no egress through the tunnel, or rules left after `off`.

### P0-22 — `block-on-drop` blocks on a drop until the tunnel is back
TUI running, `K` to `KS:Watch`, connect `wg08`. Then one command: drop the tunnel
(`pkill -x wireguard-go` on macOS, `ip link del wg08` on Linux) and probe every half second for
eight seconds.

## Adding a workflow

A workflow earns its place only if a passing automated test cannot answer it. Write literal
steps and a visible pass signal, add it to the [risk map](#pass-3-risk-map), and add it to the
smoke set only if a failure there would stop a release on its own.
