# P0 — release gate

Every workflow here must pass on **macOS and Linux** before a release ships. They are
the checks that only a real kernel, a real terminal and real protocol daemons can
answer. Anything an automated test can decide is not in this file — see
[What this file deliberately does not cover](#what-this-file-deliberately-does-not-cover).

A workflow is written so an agent can execute it with no prior knowledge of Vortix:
every step is a literal command or keystroke, and every pass signal is something you
can see in captured output. If a step needs judgement, that is a bug in the step.

**Pick a workflow by area:**

| Area | Workflows |
|---|---|
| Startup, privilege, file ownership | P0-01 – P0-06 |
| Import, rename, delete profiles | P0-07 – P0-11 |
| Connect, disconnect, reconnect | P0-12, P0-12a – P0-12e, P0-13, P0-16, P0-17 |
| OpenVPN credentials and OTP | P0-14, P0-15, P0-38 |
| Multi-tunnel, routing, takeover | P0-18, P0-18a, P0-19, P0-20 |
| Kill switch | P0-21 – P0-24 |
| DNS | P0-25 – P0-28 |
| Security Guard, telemetry, IPv6 | P0-29 – P0-32 |
| Terminal, rendering, logging, themes | P0-33 – P0-36 |
| Secrets on disk | P0-37, P0-38 |

## Harness

The dashboard is a full-screen TUI, so drive it through `tmux` and read frames back
with `capture-pane`. This is the only supported way to run the TUI workflows.

Use the user's `vxrun` session (see `CLAUDE.md`, "Live testing"): window 0 is a root pane
for the TUI, window 1 a root shell. Both are already root, so an agent never types
`sudo` — send the commands below that start with `sudo` to `vxrun:1` without it. If the
session is missing, ask the user to create it.

```bash
VX=$PWD/target/debug/vortix         # build first: cargo build -p vortix

tui()  { tmux resize-window -t vxrun:0 -x "${1:-120}" -y "${2:-40}"
         tmux send-keys -t vxrun:0 "clear; $VX" Enter; sleep 6; }
key()  { tmux send-keys -t vxrun:0 "$@"; sleep "${DELAY:-2}"; }
frame(){ tmux capture-pane -t vxrun:0 -p; }
stop() { tmux send-keys -t vxrun:0 q; sleep 2; }              # quits the TUI, keeps the pane
```

- `tui 80 24` runs the 80×24 layout the dense workflows require.
- `key 'x'` sends a character, `key Enter` / `key Escape` / `key 'D'` send named keys.
- `frame | grep -n …` is how you assert. Capture **before and after** every keystroke
  that is supposed to change something; a pass that cannot be seen in a frame is not a pass.
- The TUI needs root, and refuses outright without it (`Vortix needs administrator access`),
  so there is no unprivileged subset of any workflow below.
- **Never kill `vxrun`.** Its panes are the user's root shells; an agent cannot recreate
  them. That is why `stop()` quits the TUI and leaves the pane alive.

**Keymap** (from the `?` overlay — do not guess these):

| Key | Action | Key | Action |
|---|---|---|---|
| `c` / `Enter` | connect / disconnect focused row | `i` | import profile |
| `c` (in-flight) | cancel connect | `R` | rename profile |
| `1`–`9` | quick-connect profile N | `Del` | delete profile |
| `d` | disconnect focused row (sidebar) | `v` | view config |
| `D` | sidebar: disconnect **all** (`y`/`n` only with 2+ up); elsewhere: disconnect | `a` | manage OpenVPN auth |
| `r` | sidebar: connect; elsewhere: reconnect | `A` | clear saved auth |
| `K` | cycle kill switch | `s` | cycle sort |
| `p` | switch theme | `/` | search |
| `x` / `b` | action / bulk menu | `y` | copy IP |
| `j`/`k` | move selection | `F1`–`F5` | focus Sidebar … Logs |
| `z` | zoom panel | `f` | flip (Chart, Details, Security) |
| Logs: `f` / `L` | cycle filter / clear | `?` | help |
|  |  | `q` | quit |

## Prerequisites

| # | What | How |
|---|---|---|
| 1 | Binaries | `cargo build -p vortix` on each host for every workflow; P0-33 also needs `cargo build --release`, because it tests the `opt-level="z"` profile. |
| 2 | Real VPN endpoints | `scripts/vpn-lab.sh up` provisions one DigitalOcean droplet with all 15 named profiles. **It bills by the hour — run `scripts/vpn-lab.sh down` when the run is finished.** |
| 3 | Profiles imported | `vortix import <lab-profiles-dir>`. Workflows name profiles by their lab number (`wg07`, `03-openvpn-tcp-password-full`, …). |
| 4 | A second terminal | Several workflows need a concurrent client. `tmux new-window` is fine. |
| 5 | **Console access, if the host is remote** | Several workflows bring up a full tunnel (`AllowedIPs = 0.0.0.0/0`). On a machine you reach over SSH that captures the reply path and cuts your own session, with no way back in. Either run these on a host you can reach a console on, or keep every tunnel split-route. A `wg-quick` tunnel does not survive a reboot, so a power cycle is the recovery. |
| 6 | No competing VPN | A corporate/mesh VPN on the host owns routes and DNS and will make routing and leak workflows lie. Check with `ifconfig \| grep utun` (macOS) / `ip link` (Linux) and disconnect it first. |

Profiles used below: `wg07` split-route (`10.200.0.0/24`, `10.250.0.0/24`), `wg08`
full-tunnel with `DNS = 1.1.1.1, 1.0.0.1`, `wg11` full dual-stack, `wg14` full DNS-negative, `03-…-password-full` OpenVPN password,
`04-…-static-challenge` OpenVPN OTP, `01-…-full-inline` OpenVPN cert-only.

## A. Startup and privilege

### P0-01 — Vortix refuses cleanly when it cannot own a terminal or root
Both platforms.
```bash
$VX                                  # no sudo
sudo $VX </dev/null >/tmp/o 2>/tmp/e ; echo "exit=$?"
sudo $VX | cat
ssh <this-host> sudo vortix
```
**Pass** — unprivileged run prints `Vortix needs administrator access to manage VPN
connections.` and `Try again with: sudo vortix`. Every non-TTY invocation exits 1 with
`The Vortix dashboard needs an interactive terminal` and names the headless commands.
**Fail** — a panic, exit 101, or a `ratatui`/`~/.cargo/registry` path anywhere in the output.

### P0-02 — A first run leaves nothing group-readable
Any platform. The assertion is that Vortix creates its directories private *regardless of
umask*, so set one rather than needing a 002-default distro: `( umask 002; vortix import … )`.
```bash
rm -rf ~/.config/vortix
$VX import <profile>                 # unprivileged, before any sudo run
sudo $VX up wg07 && sudo $VX down wg07
ls -land ~/.config/vortix ~/.config/vortix/profiles ~/.config/vortix/sessions ~/.config/vortix/logs
```
**Pass** — every directory is `drwx------`, and the import succeeded.
**Fail** — any `drwxrwxr-x`/`drwxr-xr-x` (a group member can swap a profile even though
the files are 0600), or `persisted control state is not a private owner-controlled file`.
Then repeat with `chmod 755 ~/.config/vortix ~/.config/vortix/profiles; $VX list` — an
upgrade must repair a directory an older release left world-readable.

### P0-03 — An unprivileged CLI still works after a sudo session
Both platforms, from no config directory.
```bash
rm -rf ~/.config/vortix
sudo $VX          # let the TUI draw, then q
$VX list; $VX status; $VX import <path>
ls -lan ~/.config/vortix/profiles ~/.config/vortix/lifecycle.lock
```
**Pass** — all three unprivileged commands work; every file is owned by your uid.
**Fail** — any uid 0 in that listing, a permission error, or `could not open its session lock`.

### P0-04 — A second instance refuses in one sentence
```bash
tui 80 24
$VX                                  # second process, same config dir
```
**Pass** — the second process exits immediately with one plain sentence saying Vortix is
already running. The first session is unaffected. With `b` open in the first session,
Bulk Actions lists only Import Profiles and Disconnect All.
**Fail** — an errno, a backtrace, a source location, or the first session disturbed.

### P0-05 — A missing VPN tool warns once and blocks nothing else
Linux.
```bash
sudo apt remove -y wireguard-tools
tui; frame | grep -i "wireguard-tools"
```
**Pass** — exactly one `'wireguard-tools' not found` warning naming the install command.
Listing, importing and OpenVPN profiles all still work; only `up` on a WireGuard profile
fails, with a dependency error.
**Fail** — a repeating warning, or a missing tool blocking unrelated work.

### P0-06 — `vortix report` never blocks without a terminal
```bash
$VX report < /dev/null; echo "exit=$?"
$VX report | cat
ssh <this-host> vortix report
```
**Pass** — each prints the full report and exits 0 promptly.
**Fail** — any invocation hangs or loops on `Invalid choice`.

## B. Profile lifecycle

### P0-07 — Import accepts every supported shape and reports partial batches honestly
```bash
$VX import <lab-profiles-dir>        # mixed .conf/.ovpn, >8 files, one malformed
$VX import <single.ovpn> --json
$VX list
```
Then repeat the directory import from the TUI (`i`) while holding `j`/`k` to navigate.
**Pass** — every valid profile is admitted exactly once in filename order, the invalid one
is reported once, the exit code reflects partial success, and the terminal stays responsive
throughout. `--json` carries no raw config or credential material.
**Fail** — a valid profile silently dropped, the invalid one reported per-retry, a frozen
terminal.

### P0-08 — Malformed input is refused with a reason the user can act on
```bash
printf '' > /tmp/empty.conf
printf '[Interface]\nPrivateKey = x\n' > /tmp/nopeer.conf
printf '   \n\n' > /tmp/blank.conf
head -c 5000000 /dev/zero | tr '\0' 'x' > /tmp/huge.conf
cp <valid-wg> "/tmp/../../etc/passwd.conf" 2>/dev/null
for f in /tmp/empty.conf /tmp/nopeer.conf /tmp/blank.conf /tmp/huge.conf; do $VX import $f; done
```
**Pass** — each refusal names the rule it broke: `File is empty`, `Missing [Peer] section`,
`Missing [Interface] section`, `File too large … should be under 1 MB`. A filename that
cannot be a WireGuard interface names the naming rule.
**Fail** — any refusal that gives no reason, or a generic `import failed`.

### P0-10 — Rename preserves identity; delete waits for a real disconnect
```bash
sudo $VX up 03-openvpn-tcp-password-full     # save credentials when prompted
```
In the TUI: focus the connected row, press `R` (refused while active), press `Del`
(refused while active). Disconnect, then rename it, restart Vortix, connect again.
**Pass** — rename is refused with a reason while the profile is active; after disconnect
the rename keeps the same stable id, the saved credentials still work, its metadata
still points at it, and no old-name files remain. `Del` becomes available only once the
profile shows Disconnected, and is never refused for a profile displayed as disconnected.
**Fail** — a re-prompt for credentials after rename, an orphan file, or a delete accepted
mid-`Disconnecting`.

### P0-11 — A stray metadata file explains itself instead of bricking the CLI
```bash
touch ~/.config/vortix/profiles/.stray.meta.toml
$VX list
```
**Pass** — the error names that exact path, explains that Vortix tracks profiles in an
inventory, and ends with a `mv` command that makes `vortix list` work again when run verbatim.
**Fail** — a blanket `Restore the managed profile directory to its saved inventory` with no
path and no command: every command including read-only ones is then locked out with nothing to act on.

## C. Connect and disconnect

### P0-12 — A cold one-shot CLI connects and disconnects on the first try
No TUI running, profile disconnected.
```bash
sudo $VX up wg07 --timeout 60; echo "exit=$?"
$VX status; $VX status --json | jq '.data.primary'
sudo $VX down wg07; echo "exit=$?"
```
Repeat for `01-openvpn-udp-full-inline`, and repeat each in `--json` and `--quiet`.
**Pass** — the first invocation converges instead of timing out. Human mode names the
transition, the target, the deadline and Ctrl-C behaviour *before* it waits, and ends on a
success line. `--json`/`--quiet` gain no progress text. Exit categories are stable.
**Fail** — a first-run timeout that a retry fixes, or progress prose polluting structured output.

### P0-13 — The TUI drives the same lifecycle and agrees with the CLI
```bash
tui 80 24
key j; key Enter                      # connect focused profile
frame | grep -iE "connected|connecting"
```
From a second terminal run `$VX status --json` while the TUI is open.
**Pass** — both surfaces report the same generation, primary, routes, health and kill-switch
state. The header, sidebar badge and Security Guard all move together. Disconnect from the
CLI and the TUI reflects it within about a tick.
**Fail** — the two surfaces disagreeing on primary or state, or the TUI needing a restart to catch up.

### P0-14 — Rejected OpenVPN credentials reopen the prompt next time
Real password profile (`03-openvpn-tcp-password-full`).
1. Connect, enter a **wrong** password, leave *save* enabled. Let it fail.
2. Connect again.
3. Connect with the correct password, disconnect, connect a third time.
4. Press `a` (manage auth).
**Pass** — attempt 1 fails with an authentication error and a toast saying the saved
credentials were removed; attempt 2 **reopens the prompt** rather than silently failing;
attempt 3 succeeds and attempt 4 reuses the stored pair with no prompt. `a` shows no stored
credentials after the rejection. A definitive rejection leaves the profile Disconnected
with no automatic retry and no surviving `openvpn` child.
**Fail** — the second connect failing without prompting, or a correct password not remembered.

### P0-15 — The OpenVPN static challenge is one-shot and memory-only
Profile `04-openvpn-tcp-static-challenge`, username/password already saved.
```bash
sudo $VX up 04-openvpn-tcp-static-challenge
```
Answer the OTP once. Then separately: try answering twice, Ctrl-C at the prompt, let the
deadline expire, and connect from a second client while a prompt is open.
```bash
sudo ls ~/.config/vortix/auth/ | grep -i scrv1        # must be empty
grep -riE "scrv1|<the OTP>" ~/.config/vortix/
ps auxww | grep openvpn | grep -c "<the OTP>"
```
**Pass** — exactly one challenge is shown per connect attempt, only the originating
client can answer, and it can answer once. No `.scrv1.auth` file is ever written. Cancel,
expiry and termination leave no secret file, socket, process or pending reconnect, and the
next attempt prompts again. No credential material in logs, snapshots, events or `ps`.
**Fail** — any OTP or password found on disk or in a process argument list.

### P0-16 — An unreachable peer times out, cleans up, and says so
Build the broken fixture from a **split-route** profile (`wg07`: `AllowedIPs =
10.200.0.0/24, 10.250.0.0/24`, no `DNS =` line). Never from a full tunnel: `wg-quick`
installs the default route and the resolver *before* the handshake is attempted, so a
connect that then fails can strand the machine with its egress and DNS pointing into a
tunnel that has nothing behind it. That is how this workflow took a laptop off the
network — the failure is the point of the test, so the fixture must not be able to carry
the whole machine with it.
```bash
sed 's/^Endpoint =.*/Endpoint = 192.0.2.99:51820/' wg07.conf > /tmp/wgdead.conf   # split route
$VX import /tmp/wgdead.conf
sudo $VX up wgdead --timeout 30
```
Do the same for an OpenVPN endpoint that starts but never reaches
`Initialization Sequence Completed`.
**Pass** — WireGuard stays `Handshaking` and never claims Connected or Protected; the
attempt ends at the configured timeout; the profile returns to Disconnected; cleanup
removes the exact interface / OpenVPN process **without reconnecting**;
the header and sidebar stop showing Connecting; an immediate retry is accepted.

**Also assert the host is still usable after each attempt**, including the retry:
```bash
netstat -rn -f inet | awk '$1=="default"{print $2, $NF}'   # must not name a tunnel device
curl -4 -s --max-time 8 https://ifconfig.me/ip              # must answer
```
A failed connect that leaves the default route or resolver pointing into a dead tunnel
does not recover on its own — the operator has to kill the process by hand.
**Fail** — a silent reconnect loop, a leftover interface or `openvpn` process, or a UI stuck in Connecting.

### P0-17 — Disconnect reaches terminal truth without a restart
```bash
sudo $VX up wg07; sudo $VX up 01-openvpn-udp-full-inline
sudo $VX down wg07                    # leave the other up
```
Repeat with the tunnel killed out from under Vortix first
(`sudo pkill openvpn` / `sudo ip link delete <iface>`), then disconnect normally.
**Pass** — the selected profile leaves `Disconnecting` as soon as protocol-owned absence is
proven, the other stays Connected, and closing/reopening the TUI is never required. Both the
clean and the already-gone path report a plain disconnect — no `DNS read-back is degraded`
and no `Disconnect could not finish safely`.
**Fail** — a profile stuck in `Disconnecting`, a stale presence restored by a late scan, or
`resolvectl status` still listing Vortix DNS on a dead link.

### P0-12a — Lifecycle verbs are idempotent and say so
Measure exit codes directly (`cmd >/dev/null 2>&1; echo $?`) — a pipe into `tail`
reports the pipe's status, not Vortix's.

| Command | Expected output | Exit |
|---|---|---|
| `up <profile>` twice | second prints `● Connected to <profile> (<proto>)` | 0 |
| `down <profile>` twice | second prints `Already disconnected` | 0 |
| `down <never-connected>` | `Already disconnected` | 0 |
| `down` with no argument | `Disconnecting active VPNs …` then each profile | 0 |
| `up no-such-profile` | `Profile 'no-such-profile' not found` + `Run 'vortix list'` hint | 3 |
| `up <overlapping>` | names **both** profiles and the `--yes` bypass | 4 |
| `import <malformed>` | names the rule broken | 1 |

**Pass** — every row matches, and `down` with no argument leaves zero tunnel interfaces.
**Fail** — an exit code that does not distinguish not-found (3) from conflict (4) from a
general failure (1), or an idempotent repeat that errors.

### P0-12b — Two clients racing the same profile produce one tunnel
```bash
sudo $VX down wg08
( sudo $VX up wg08 --timeout 60 >/tmp/a1 2>&1 ) &
sleep 1
( sudo $VX up wg08 --timeout 60 >/tmp/a2 2>&1 ) &
wait; tail -1 /tmp/a1; tail -1 /tmp/a2
ip -brief link show | grep -c wg08        # Linux → 1
```
**Pass** — both clients print `● Connected to wg08 (…)`, both exit 0, and exactly **one**
interface exists.
**Fail** — two interfaces, or a duplicate protocol child.

### P0-12c — `reconnect` ends connected, or changes nothing
```bash
sudo $VX up wg08 --timeout 60
curl -4 -s --max-time 10 https://api.ipify.org     # the VPN exit
sudo $VX reconnect wg08 ; echo "exit=$?"
curl -4 -s --max-time 10 https://api.ipify.org     # must still be the VPN exit
$VX status --json | jq -c '{p:.data.primary,c:[.data.connections[].profile]}'
sudo $VX reconnect                                  # no argument: cycles every active tunnel
```
`reconnect` takes no `--timeout`; passing one is a parse error.
**Pass** — the profile is Connected afterwards, the egress address is still the VPN's, and
`primary` still names it. If the reconnect genuinely fails, the tunnel is either restored or
the message says the tunnel is now **down** — never "nothing was changed".
**Fail** — a message claiming nothing changed while the tunnel is gone and egress has
returned to the real ISP address. That is the worst outcome: the user believes they are still
protected.

### P0-12d — Every protocol variant in the matrix connects and tears down clean
Connect and disconnect each, one at a time, asserting the interface count returns to zero:
```bash
for p in wg09 wg10 wg12 wg13 wg15 01-openvpn-udp-full-inline 05-openvpn-udp-multi-remote; do
  sudo $VX up $p --timeout 60 2>&1 | tail -1
  sudo $VX down $p >/dev/null 2>&1
done
ip -brief link show | grep -cE 'wg|tun'   # → 0
```
Coverage: hostname endpoint (`wg09`), IPv6 endpoint (`wg10`), preshared key (`wg12`),
two peers with disjoint routes (`wg13`), explicit `FwMark` (`wg15`), OpenVPN inline
certificate (`01`), and OpenVPN whose first remote is unreachable so it must fail over (`05`).
**Pass** — each reports `● Connected`, `wg13` installs **both** peer routes
(`ip route show | grep -cE '10.200.0.0/24|10.201.0.0/24'` → 2), `05` reaches the working
remote after the dead one, and the final interface count is zero.
**Fail** — any variant failing to connect, or any leftover interface after the loop.

### P0-12e — Rapid and interrupted lifecycle actions leave no debris
Each case starts from disconnected and ends with the interface count back at zero.
```bash
count() { ip -brief link show | grep -cE 'wg|tun'; }   # macOS: ifconfig | grep -c '^utun[4-9]'
```

`1`-`9` quick-connect the profile at that index; `d` disconnects the focused row; `D` with
the sidebar focused disconnects all (confirming only when two or more are active).

| # | Action | Expected |
|---|---|---|
| a | `up wg08 &`, then `down wg08` ~2 s later | both report their own outcome; ends disconnected, count 0 |
| b | `up wg08 &`, then `up wg09 --yes` ~2 s later | both connect; count 2; each owns its declared routes |
| c | `up`/`down` the same profile 5× back to back | ends disconnected, count 0, no stuck `Connecting` |
| d | `up wg08`, `down wg08`, `up wg09` with no settle | wg09 connected, count 1 |
| e | SIGINT the client mid-connect | see below |
| f | TUI: `Enter` then `c` while the row shows `◐` | row returns to disconnected, count 0 |
| g | TUI: `7`,`8`,`9` 0.2 s apart | **all three** connect; count 3 |
| h | TUI: after (g), `Shift+D` then `Y` | count 0 and **stays** 0 — no tunnel appears afterwards |
| i | TUI: `Shift+D` with nothing connected | no dialog, stays disconnected |
| j | TUI: `d` on a row that is not connected | nothing disconnects |

**Pass** — every row lands on its expected state, the interface count returns to zero at the
end of each case, and no `openvpn` process survives (`pgrep -c openvpn` → 0). A second
profile connecting while the first is in flight must not cancel or adopt the first.
**Fail** — a stuck `Connecting`, an interface left behind, or two clients both claiming the
same tunnel.

**Case (e) is the sharp one.** There is no SIGINT handler in the CLI, so Ctrl-C stops *this
process waiting* — the connect continues and can still bring the tunnel up. What
must be true afterwards is that Vortix still knows about it:
```bash
sudo $VX up wg08 --timeout 60 &   # then SIGINT the process group ~5 s in
ip -brief link show | grep -c wg08        # may legitimately be 1
$VX status                                 # must NOT say Disconnected while that is 1
curl -4 -s --max-time 8 https://api.ipify.org
```
**Fail** — `status` reporting `Disconnected` and `primary: null` while the interface exists
and `curl` returns the VPN's exit address. That is traffic flowing through a tunnel the
product says is not there, and the user has no way to know they are on it.

## D. Multi-tunnel and routing

### P0-18 — Two tunnels own the routes they claim
```bash
sudo $VX up wg08                      # 0.0.0.0/0
sudo $VX up wg07                      # split, 10.200.0.0/24 + 10.250.0.0/24
ip route get 1.1.1.1 ; ip route get 10.200.0.1      # Linux
route -n get 1.1.1.1 ; route -n get 10.200.0.1      # macOS
curl -s --max-time 10 https://api.ipify.org
sudo nft list table inet vortix_killswitch | grep -E "wg08|wg07"  # Linux
sudo pfctl -a com.apple/vortix.killswitch -sr        # macOS
```
**Pass** — the default route resolves to the full-tunnel device and the split destination to
the split device; the public IP is the full tunnel's exit; the firewall has a per-tunnel
ACCEPT/pass-out for each interface and carves the split tunnel's declared CIDR. The sidebar
marks exactly one primary (`*`) and it matches the kernel.
**Fail** — a split tunnel holding the default route, or the sidebar naming a primary the kernel disagrees with.

### P0-18a — A `redirect-gateway def1` full tunnel is the exit, never "no exit"
OpenVPN's standard `redirect-gateway def1` installs `0.0.0.0/1` + `128.0.0.0/1` and leaves the
kernel's literal `default` route on the LAN, so a naive read of the `default` slot mistakes a
full tunnel for a split one. Connect such a profile from the TUI and confirm Vortix reads the
real exit. Repeat the connect several times — the fault is a timing race and only shows on
some connects.
```bash
tui
key j; key Enter; sleep 30            # connect the full-tunnel OpenVPN profile
ip route get 8.8.8.8                   # Linux: resolves via the tun device
curl -s --max-time 10 https://api.ipify.org   # the VPN exit IP, not your ISP
frame | grep -iE "role|exit ip|dns|no exit"
```
**Pass** — `ip route get 8.8.8.8` resolves through the tun device and the public IP is the
VPN's exit; the header shows `CONNECTED` (not `NO EXIT`), Connection Details `Role` reads
`Primary`, and the Security Guard `Exit IPv4` shows the VPN address with a check — even though
`ip route show default` still points at the LAN. The `DNS` row shows the pushed resolver with
its provider and a check (`Protected`), never `Not provided` while the resolver is applied.
Every successful connect elects the tunnel as primary; the state never gets stuck and never
needs a TUI relaunch to correct itself.
**Fail** — a connected full tunnel rendered as `NO EXIT` / `Role: Split tunnel (0.0.0.0/0)` /
`Exit: split-route — no exit`, or a `DNS: Not provided` row, while traffic actually exits
through the tunnel.

### P0-19 — A route conflict offers Switch or Cancel, never a dead end or a hang
With `wg08` connected and owning the default route, connect a second full-tunnel profile —
once from the TUI directly, and once by claiming the route from a **second client**
(`$VX up <other>` in another terminal) so the conflict lands after the TUI's last snapshot.
**Pass** — the `Already connected` confirmation opens naming both profiles and the destructive
default, and offers exactly two resolutions: `[Y] Switch` (disconnect the first, connect the
new) and `[Esc]`/`[N] Cancel` (leave the first untouched). `Y`/`Enter` switches; `N`/`Esc`
cancels with no relaunch. A key that is neither — including `b`/`B` — is inert: the modal stays
open and the TUI keeps responding. A conflict the service refuses still surfaces the confirmation.

## E. Kill switch

> **These workflows deliberately cut your egress.** `vpn-only` installs a terminal
> `block drop out quick all` / default-DROP OUTPUT and permits only the tunnel interface and
> the VPN endpoint. If the tunnel goes away while the policy is installed, **all traffic
> stops** — that is the feature working. Before starting, know the recovery by heart:
>
> ```bash
> sudo vortix release-killswitch          # takes no --yes; only -C/--config-dir
> ```
>
> Never put the recovery behind a flag you have not verified, and never rely on a shell
> `trap` for it: if the release command fails to parse, the trap still tears the tunnel down
> and you are left blocked. Run the release as an explicit, checked step and confirm the
> anchor is empty before moving on.

Vocabulary is fixed: `off`, `block-on-drop`, `vpn-only`. There are no aliases.

### P0-21 — `vpn-only` engages immediately and holds through a drop
```bash
sudo $VX up wg08
sudo $VX killswitch vpn-only
sudo nft list table inet vortix_killswitch        # Linux
sudo pfctl -a com.apple/vortix.killswitch -sr     # macOS
sudo wg-quick down wg08                           # drop it externally
sudo nft list table inet vortix_killswitch | grep "policy drop"  # Linux, still dropping
curl -m 5 https://example.com; echo "curl=$?"
```
**Pass** — the firewall read-back shows the Vortix-owned terminal block policy *while the VPN
is still up* (not `Armed` with no enforcement), egress is blocked during the gap between drop
and reconnect, and no ICMP escapes. `$VX killswitch` and the Security Guard both say
`VPN-only`, never a raw enum name.
**Fail** — `Armed`/`Watching` while `vpn-only` is selected, or any egress succeeding during the gap.

### P0-22 — `block-on-drop` reports the block it actually engaged
```bash
sudo $VX killswitch block-on-drop
sudo $VX up wg08
sudo ip link delete wg08              # or: sudo pkill openvpn
curl -m 5 https://example.com; echo "curl=$?"
sudo nft list table inet vortix_killswitch
```
**Pass** — egress is blocked, the table shows the barrier, the header reads `KS:DROPPED` and
Security Guard says `Killswitch: VPN dropped` with `press r to reconnect` — and it **holds for
several minutes**, not five seconds. With the VPN merely connected and no drop, the table does
not exist, `$VX killswitch` prints `Watching`, and the row stays `Block on drop` for five
minutes without flipping to `Degraded`.
**Fail** — `KS:DEGRADED` at any point while that table is present and correct, the row
oscillating between the two, or a `Degraded` row while the table is genuinely absent.
Then make a reconnect fail past the tunnel barrier: the pre-tunnel barrier must **stay
installed** (fail-closed) and keep reading `KS:DROPPED` over it — never torn down by failure
compensation, never installed-but-unreported.

## Adding a workflow

A new workflow earns its place only if a passing automated test cannot answer it. Write the
steps as literal commands and keystrokes, and write the pass signal as something visible in a
captured frame or command output. If the pass signal needs a judgement call, it is not ready.
Add a row to the results log in the same commit.
